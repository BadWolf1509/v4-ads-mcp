# Sprint 3b.2 — `update_ad_status` + `bulk_pause_by_query`

**Date:** 2026-05-11
**Author:** Wellinton Ribeiro + Claude (Sonnet 4.7)
**Status:** Design approved, pending implementation plan
**Phase:** Second sprint of Phase 3b (advanced mutations backlog)

---

## 1. Goal

Ship the next two mutation tools of the Phase 3b backlog. Both are low-quota and don't depend on Standard Access. The pair together unblocks two high-frequency workflows from the `analise-performance-google-ads` skill:

1. **Pause individual ads** without affecting their ad_group (granularity gap in Phase 3a).
2. **Bulk pause by GAQL query** — automation of "pause keywords/ads/campaigns matching criteria" that today is manual N-shot.

**Definition of done:**

1. `update_ad_status` MCP tool registered, dispatches with bulk-aware classification (≤5 = AUTO, >5 = CONFIRM) + REMOVED always CONFIRM.
2. `bulk_pause_by_query` MCP tool registered, always-CONFIRM via dry-run + `apply_change` flow.
3. `blast_radius.classify` extended to recognize `new_status="REMOVED"` and always classify as CONFIRM, retrofitting the same fix into `update_campaign_status`/`update_ad_group_status`/`update_keyword_status` for free.
4. Hard limit 100 entities per `bulk_pause_by_query` call, with **hard-reject** (no silent truncation) when exceeded.
5. Telemetry `{target_type, filter_hash, query_matched_count, applied_count, failed_count, limit_hit}` in `audit_log.params_summary` for re-tuning after 4 weeks of solo-dogfood data.
6. 13 unit tests + 2 integration tests added; all 150+ existing tests still pass.
7. ruff + format + mypy + pytest unit all green locally and in CI.
8. Both tools manually smoke-tested on real V4 accounts via the smoke runbook at [`docs/operacao/phase-3b-2-bootstrap.md`](../../operacao/phase-3b-2-bootstrap.md).

**Non-goals (YAGNI):**

- Not implementing `bulk_enable_by_query` / `bulk_remove_by_query` (pause first; demand-driven later).
- Not supporting target types beyond {campaign, ad_group, ad, keyword} in `bulk_pause_by_query`.
- Not allowing mixed target types in one call (one type per call; chain if needed).
- Not exposing properties beyond `status` for `bulk_*` (only pause; budget/bid changes have their own tools).
- Not adding `bulk_pause_by_query` filter expressivity beyond GAQL WHERE-clause patterns (no subqueries, no joins).

## 3. Tool: `update_ad_status`

### 3.1 Purpose

Granular ad-level status control. Mirrors `update_ad_group_status` exactly but targets `ad_group_ad` resources. Closes the gap that today forces gestores to either pause whole ad_groups or use the Google Ads UI to pause individual ads.

### 3.2 Input schema

```json
{
  "type": "object",
  "properties": {
    "customer_id": { "type": "string", "pattern": "^[0-9]{10}$" },
    "ads": {
      "type": "array",
      "minItems": 1,
      "maxItems": 500,
      "items": {
        "type": "object",
        "properties": {
          "ad_group_id": { "type": "string", "pattern": "^[0-9]+$" },
          "ad_id": { "type": "string", "pattern": "^[0-9]+$" }
        },
        "required": ["ad_group_id", "ad_id"],
        "additionalProperties": false
      }
    },
    "new_status": { "type": "string", "enum": ["ENABLED", "PAUSED", "REMOVED"] }
  },
  "required": ["customer_id", "ads", "new_status"],
  "additionalProperties": false
}
```

### 3.3 Classification

Calls `blast_radius.classify(operation="update_ad_status", params={target_count, new_status})`. The classifier returns:

- **CONFIRM** if `new_status == "REMOVED"` (regardless of count) — per spec §7.1 "Remove qualquer coisa = sempre confirm"
- **AUTO** if `target_count <= 5` AND `new_status != "REMOVED"`
- **CONFIRM** if `target_count > 5`

The same `new_status`-aware logic retrofits into `update_campaign_status`, `update_ad_group_status`, and `update_keyword_status` (which previously missed the REMOVED-always-confirm rule).

### 3.4 AUTO output

```json
{
  "status": "applied",
  "operation": "update_ad_status",
  "customer_id": "1234567890",
  "applied_count": 3,
  "google_request_id": "...",
  "blast_summary": "Mudar status de 3 anuncio(s) para PAUSED.",
  "auto_applied_reason": "..."
}
```

### 3.5 CONFIRM output

```json
{
  "status": "dry_run",
  "operation": "update_ad_status",
  "customer_id": "1234567890",
  "confirmation_token": "ABC12345",
  "expires_in_minutes": 10,
  "blast_summary": "Mudar status de 10 anuncio(s) para PAUSED.",
  "to_apply": "Chame apply_change(confirmation_token=<token>) para aplicar.",
  "confirmation_reason": "..."
}
```

### 3.6 Mutate path

`run_mutation(operation_type="update_ad_status", payload={ads, new_status, __target_count__})`. The new builder `build_update_ad_status` in `src/google_ads/mutates/ads.py`:

- For each `(ad_group_id, ad_id)` tuple, emits an `ad_group_ad_operation.update` MutateOperation
- Resource path: `customers/{cid}/adGroupAds/{ad_group_id}~{ad_id}`
- Sets `update_mask = ["status"]`
- Sets `status = AdGroupAdStatusEnum[new_status]`

## 4. Tool: `bulk_pause_by_query`

### 4.1 Purpose

Operationalize "pause N entities matching a GAQL filter" as a single dry-run + apply cycle. Today, gestores using the `analise-performance-google-ads` skill identify pause candidates with GAQL but execute N individual mutations. This tool collapses that to one preview-then-apply round trip.

### 4.2 Input schema

```json
{
  "type": "object",
  "properties": {
    "customer_id": { "type": "string", "pattern": "^[0-9]{10}$" },
    "target_type": { "type": "string", "enum": ["keyword", "ad", "campaign", "ad_group"] },
    "filter": {
      "type": "string",
      "minLength": 1,
      "maxLength": 1000,
      "description": "WHERE clause body (no SELECT/FROM/LIMIT/ORDER BY, no semicolons)."
    },
    "date_range": {
      "default": "LAST_30_DAYS",
      "description": "Auto-injected as segments.date BETWEEN when filter mentions metrics.* and no segments.date is already in the filter."
    }
  },
  "required": ["customer_id", "target_type", "filter"],
  "additionalProperties": false
}
```

### 4.3 Filter validation

Pre-flight checks, all returning friendly PT-BR errors:

| Check | Behavior |
|---|---|
| Contains `;` | Reject — multi-statement attempt |
| Contains case-insensitive `SELECT `, `FROM `, `LIMIT `, `ORDER BY` | Reject — only WHERE clause body allowed |
| Length > 1000 chars | Reject — too long |
| Mentions `metrics.` but no `segments.date` AND no `date_range` param | Inject `segments.date BETWEEN <start> AND <end>` derived from `date_range` (default LAST_30_DAYS) |

Google's GAQL parser handles syntax errors after we pass the pre-flight gate. We let Google reject with its own error message, then translate via `to_friendly()`.

### 4.4 Target-type to GAQL mapping

| target_type | FROM resource | Mutate target | Notes |
|---|---|---|---|
| `keyword` | `keyword_view` | `ad_group_criterion` | metrics available on keyword_view; mutate uses criterion_id + ad_group_id from query |
| `ad` | `ad_group_ad` | `ad_group_ad` | metrics + entity on same resource |
| `campaign` | `campaign` | `campaign` | same |
| `ad_group` | `ad_group` | `ad_group` | same |

For each target_type, the internal GAQL is templated as:

```sql
SELECT <id_fields>, <name_fields>, <status_field>, metrics.cost_micros
FROM <resource>
WHERE <date_clause_if_metrics> AND <user_filter>
LIMIT 101    -- 100 + 1 for overflow detection
```

The `LIMIT 101` is the key trick: if the query returns ≥101 rows, we know the count exceeds our cap without running a separate `COUNT()` query.

### 4.5 Dry-run flow

```
1. Validate target_type against enum (schema-level)
2. Validate filter (§4.3 checks)
3. Build internal GAQL per target_type (§4.4)
4. run_report(operation_name="bulk_pause_by_query", audit_this_call=True)
5. Decide based on row count:
   - 0 rows           → return {status:"no_op", matched_count:0, message:"Nenhuma entidade matched..."}
   - ≤100 rows        → capture, build preview, create_pending, return token
   - ≥101 rows        → return {status:"error", error:"Sua query matched X+ entidades — acima do limite...", matched_count: N}
6. On token creation: payload = {target_type, entities: [...], total_cost_brl}
   pending_confirmations stores via spec §7.2 mechanism
```

### 4.6 Apply flow (via `apply_change`)

`apply_change` already exists. It consumes the token and dispatches to `run_mutation(operation_type="bulk_pause_by_query", ...)`. The new builder `build_bulk_pause` in `src/google_ads/mutates/bulk.py`:

```python
@register_builder("bulk_pause_by_query")
def build_bulk_pause(client, customer_id, payload):
    target_type = payload["target_type"]
    entities = payload["entities"]
    ops = []
    for entity in entities:
        op = client.get_type("MutateOperation")
        if target_type == "keyword":
            # ad_group_criterion update
            ag_id = entity["ad_group_id"]
            crit_id = entity["criterion_id"]
            crit_op = op.ad_group_criterion_operation
            crit = crit_op.update
            crit.resource_name = f"customers/{customer_id}/adGroupCriteria/{ag_id}~{crit_id}"
            crit.status = client.enums.AdGroupCriterionStatusEnum.PAUSED
            crit_op.update_mask.paths.append("status")
        elif target_type == "ad":
            # ad_group_ad update — analogous
            ...
        elif target_type == "campaign":
            ...
        elif target_type == "ad_group":
            ...
        ops.append(op)
    return ops
```

Run via `run_mutation(partial_failure=True, params_summary={...telemetry...})`. The response classifies each row by `WhichOneof("response")` per Sprint 3b.1 pattern (`paused` vs `failed`).

### 4.7 Output shapes

**Dry-run, no matches:**
```json
{
  "status": "no_op",
  "operation": "bulk_pause_by_query",
  "customer_id": "1234567890",
  "matched_count": 0,
  "message": "Nenhuma entidade matched o filtro. Nada a pausar."
}
```

**Dry-run, exceeds cap:**
```json
{
  "status": "error",
  "operation": "bulk_pause_by_query",
  "matched_count": "100+",
  "error": "Sua query matched 100+ entidades — acima do limite de 100 por chamada (decisão MVP). Refine o filtro pra reduzir alcance, ou divida em múltiplas chamadas. Ex: adicionar AND segments.date DURING LAST_7_DAYS, filtrar campaign.id específico, ou metricas mais restritivas."

```

(Note: `matched_count` is a `string` here — `"100+"` — to disambiguate from the integer used in the valid `dry_run` case. Type discriminator is `status` (`"error"` vs `"dry_run"`) — callers branch on that.)

### 4.8 Audit log telemetry

`pending_confirmations` table doesn't currently get audit_log rows (only `apply_change` does). For the dry-run we rely on `run_report(audit_this_call=True)` writing a "read" audit row with `params_summary=None`. We extend this to pass a custom `params_summary` (requires also extending `run_report` to accept `params_summary` like `run_mutation` does post-Sprint 3b.1).

**Dry-run audit row (`action_type=read`, `operation=bulk_pause_by_query_dry_run`):**
```json
{
  "target_type": "keyword",
  "filter_hash": "sha256:<hex>"
}
```

(Architectural note: `run_report` captures `params_summary` at call-time
— before row count is known — and writes the audit row in its `finally:`
block. Dynamic fields like `query_matched_count` or `limit_hit` would
require either a run_report API extension or a separate audit row. For
Sprint 3b.2 MVP, the dry-run audit captures only the static metadata
that's known before the query runs. The apply audit row, which fires
later via `run_mutation`, includes `__target_count__` via the default
`{keys: sorted(payload.keys())}` summary — so the count IS audited,
just on the apply side, not the dry-run side.)

**Apply audit row (`action_type=mutate`, `operation=bulk_pause_by_query`):**
```json
{
  "target_type": "keyword",
  "filter_hash": "sha256:<hex>",
  "applied_count": 45,
  "failed_count": 2
}
```

`filter_hash` is SHA-256 of the raw filter string. Audits the existence + cardinality of distinct filter patterns over time without storing the filter itself (filters may carry competitive intel — e.g., listing competitor brand names).

## 8. Risks & mitigations

| Risk | Likelihood | Mitigation |
|---|---|---|
| User-supplied filter contains SQL/GAQL-like injection | Low (Google parser is sandbox) | Pre-flight rejects `;`, `SELECT/FROM/LIMIT/ORDER BY`, length>1000. Audit stores SHA-256 hash, not raw filter. |
| Entity removed between dry-run and apply (10-min window) | Medium | `partial_failure=True` captures per-op failure; surfaced in `results[].status` |
| Hard cap 100 too low for real workflows | Medium | Telemetry `query_matched_count` + `limit_hit` in audit; re-tune from solo-dogfood data after 4 weeks |
| `target_type=keyword` confusion (query keyword_view but mutate ad_group_criterion) | Medium | Dedicated builder test per type; module docstring explains mapping |
| User runs `metrics.*` filter without date | High | Auto-inject `segments.date BETWEEN` from `date_range` (default `LAST_30_DAYS`) when filter mentions `metrics.` and no date filter |
| Sprint 3b.1-style API surface bug masked by mocks | Low-medium | At least 1 integration test uses proto-plus-like fixture (`SimpleNamespace`-based, not `MagicMock`) — same pattern as Sprint 3b.1 final fix |
| REMOVED gap in existing 3 status ops (Phase 3a) | Already-present bug | Retrofit `blast_radius.classify` to accept `new_status`; all 4 status ops now correctly require CONFIRM on REMOVED |

## 9. Open questions — resolved

| Question | Resolution |
|---|---|
| Hard cap for `bulk_pause_by_query` | **100 entities**, hard-reject (no silent truncation). Re-tune after 4 weeks via `limit_hit` telemetry. |
| API shape — raw GAQL vs structured | **Structured** (`target_type` + `filter`). Safer + easier to validate + clearer error messages. |
| MVP target types | **4 types**: campaign, ad_group, ad, keyword. Covers 95% of `analise-performance` workflows. |
| Filter audit logging | **SHA-256 hash** in `audit_log.params_summary`. Filters may carry competitive intel (competitor names, brand strategy hints). |
| `date_range` injection when filter uses metrics | **Auto-inject** with default `LAST_30_DAYS` when filter mentions `metrics.*` and has no `segments.date`. |
| Sample size in preview | **10 entries** — legible, sufficient to catch filter errors. |
| REMOVED-always-confirm | **Yes**, retrofitted into `blast_radius.classify` (fixes existing gap in 3 Phase 3a status ops too). |
| `bulk_pause_by_query` other ops (enable/remove) | **Not in MVP** — pause first; demand-driven later. |
| Dry-run audit row count fields | **Defer to apply audit.** `run_report` can't populate dynamic fields at call-time; documenting the architectural limitation rather than building a workaround for MVP. |

## 10. Out of scope (explicit)

- **`bulk_enable_by_query`, `bulk_remove_by_query`** — only pause for MVP.
- **Mixed target types in one call** — one type per call; chain if needed.
- **GAQL subqueries / joins** — not supported by Google Ads API; out of scope here.
- **Modifying properties other than `status`** — budget/bid changes have dedicated tools.
- **Targeting `asset`, `conversion_action`, `audience`** — out of workflow scope.
- **Bulk-mutate other than pause-derived ops** — bid changes, budget changes, etc., have their own dedicated tools or future sprints.
