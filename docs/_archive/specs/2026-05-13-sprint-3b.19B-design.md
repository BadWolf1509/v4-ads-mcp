## Goal

Adicionar MCP tool `create_conversion_value_rule_set` para que gestor V4 configure regras de valor condicional sobre as ConversionActions criadas em Sprint 3b.19A. Resolve gap recorrente em V4 onde "valor de conversão padrão" não reflete heterogeneidade real (e.g., compra desktop costuma valer mais que mobile; lead SP converte 2x mais que interior).

Esta sprint complementa o **tracking setup loop**: 3b.19A criou a conversion action ENABLED com `default_value_brl` único; 3b.19B permite refinar esse valor condicionalmente via rules.

## Context / why now

- **Sinal de produto:** dogfood expansion de 3b.19A criou 14 ConversionActions em Nutry sandbox, todas com value único (R$1 default ou R$50 fixed). Real V4 use case requer device/geo discrimination — métricas devem refletir realidade comercial.
- **Low quota:** ~1-2 mutations per setup (1 RuleSet com N rules chained = single quota op).
- **Sem dependência de Standard Access verdict** — RuleSet creation funciona sob Basic Access (case `26521440673` em monitoramento passivo).
- **Padrão consolidado:** 19 sprints de create/update/remove patterns — quarto create-pattern shipping (após `create_ad_group`/3b.14 + `create_rsa`/3b.16 + `create_conversion_action`/3b.19A).
- **Cross-cutting features herdadas:** F13 (resource_names auto-returned via run_mutation, Sprint 3b.15) — testará chained mutation case for first time.
- **Sprint 3b.19A.1 lesson aplicado:** smoke runbook inclui explicit per-value empirical probe step (T6) para todos os novos enums — previne F17/F18/F19-class design gaps.

## Non-goals (v0)

- **AUDIENCE conditions** — sprint futura. Dependency em apply_audience patterns + user_list/user_interest resource paths. Não V4 core use case.
- **ITINERARY conditions** — travel niche (advance booking window, travel length); YAGNI v0.
- **Update RuleSet / RuleSet status changes** — sprint futura se demanda surgir.
- **Remove RuleSet / Remove ConversionValueRule** — sprint futura se demanda.
- **ConversionValueRule standalone create** — useless primitive sem RuleSet attachment.
- **Geo target SUGGESTION helper** (search by name → resource path) — gestor passa resource paths direct v0; sprint futura `list_geo_targets_by_name` se demanda.
- **conversion_action_categories filter via SDK enums fora do 3b.19A whitelist** — reuse 13 categorias V4-focused validadas em 3b.19A.

## Tool surface

### Name
`create_conversion_value_rule_set`

### Description (PT-BR, dispatch hint to LLM)
```
Cria 1 ConversionValueRuleSet (customer-level ou campaign-level) com 1-10
ConversionValueRule(s) nested. Always-CONFIRM. Rules condicionais ajustam o
valor de conversão por device (MOBILE/DESKTOP/TABLET) ou geo (geo_target_constants
resource paths). Action operations: ADD (soma valor fixo), MULTIPLY (multiplica),
SET (sobrescreve). Optional conversion_action_categories filter — quando omitido
aplica todas conversion actions; quando fornecido aplica só às categories listadas
(reuse 13 categorias V4-focused da Sprint 3b.19A: PURCHASE, SUBMIT_LEAD_FORM, etc).
attachment_type=CAMPAIGN requer campaign_id; CUSTOMER aplica conta inteira.
NO_CONDITION rule é fallback default (sem device/geo filter). v0 NÃO suporta
AUDIENCE/ITINERARY conditions (sprints futuras).
```

**Runtime constraints** (enforced em tool handler ou builder):
- `condition_type=DEVICE` requires `device_condition` field; rejects `geo_condition`
- `condition_type=GEO_LOCATION` requires `geo_condition` field; rejects `device_condition`
- `condition_type=NO_CONDITION` rejects both `device_condition` and `geo_condition`

## Risks & mitigations

| Risk | Mitigation |
|---|---|
| Chained mutation temp resource name pattern não funciona | Validate via context7 + smoke T1 catches. If broken, fallback para 2-API-call pattern (rules first, then set) — known Google Ads pattern, ~30 min refactor |
| `geo_target_constants` validation requires runtime GAQL query | Pre-flight helper handles. If gestor passa typo (US geo), rejects with clear PT-BR message |
| Per-value probe T6 reveals F2x findings (design gaps em new enums) | Expected by Sprint 3b.19A.1 lesson — fix em 3b.19B.1 follow-up sprint (mirror 3b.19A.1 pattern) |
| Rule order matters (Google applies first-match) but schema doesn't enforce | Document em tool description that rules are evaluated in order; gestor controla via array ordering. YAGNI explicit priority field v0 |
| dimensions field inferred from rule condition_types — what if mismatch? | Builder ALWAYS infers dims from rule set's actual conditions, ignoring any explicit dims input. Avoids inconsistent state |
